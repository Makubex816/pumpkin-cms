# Pumpkin API S2 capacity acceptance V2.8.63CRST

S2/two-worker capacity acceptance requires more than healthy platform metrics. A candidate must pass the first routed identity request on every fresh worker, the full sequential warm and cold schedules, five normal-load cycles per role, and the two-request moderate burst. Each outcome must remain below ten seconds, each locator stage below five seconds, with no timeout, HTTP 500, worker-dependent result, duplicate audit, or password mutation.

A restart or delay may identify a readiness threshold, but an operator-enforced sleep is not a production routing guarantee. When the app has a dependency-specific startup interval, the immutable candidate must expose a truthful endpoint and App Service must be configured to withhold traffic and swap completion until that endpoint returns HTTP 200.

CRST scaled exactly to S2/two workers and showed acceptable capacity: Stage A peaked at 73 percent CPU and 82 percent memory with zero queue; the stabilized Stage B proof peaked at 78 percent CPU and 80 percent memory with zero queue. Each passing 18-request schedule included five sequential cycles per role and a two-request moderate burst. Across the official final runs, maximum thread-pool pending work was three, at least 32,764 worker threads remained available, and maximum per-request process CPU was 6,375.815 ms. Nevertheless, first identity traffic returned HTTP 503 at 38.19 and 28.74 seconds after fresh starts, while the same package passed 18/18 after 136.542 seconds. Because no enforceable readiness gate existed, S2 capacity was adequate but candidate availability was not production-safe. The task therefore closed as `blocked_three_corrected_slot_candidate_cycles_failed` without promotion.
