# Tenant CMS Visual Persistence Decision V2.8.61OSI

## Platform Decision

An accepted compiled tenant fixture may remain temporarily in production after complete route, visual, form, isolation, and runtime proof. It must not be represented as authoritative CMS state.

For Party Pros, retain the proven 242-route fixture while a later separately approved phase persists the accepted graph into CMS records.

## Required Persistence Model

- Reconcile existing page/theme/form/navigation/media records before any write.
- Preserve the accepted catalog, category, event, and item route graph.
- Persist structured blocks and public media references, not raw static HTML.
- Keep required consent aligned across FormDefinition, renderer, serialized payload, and API validation.
- Update package compiler and intake standards so the accepted graph is reproducible.
- Require safe visual-reference link/image inventory for future tenants when source material exists.
- Back up, read back, and prove rollback before switching runtime authority.
- Require owner visual and functional parity acceptance before removing the fixture.

## Readiness Effect

Deferred CMS persistence is technical debt but is not a Party Pros public-readiness blocker because the current fixture has complete live proof and remains unchanged. It must be tracked independently and must not be combined with next-tenant creation without explicit owner approval.
