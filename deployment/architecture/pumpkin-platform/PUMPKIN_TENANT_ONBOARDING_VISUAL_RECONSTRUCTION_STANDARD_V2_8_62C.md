# Pumpkin Tenant Onboarding Visual Reconstruction Standard V2.8.62C

## Principle

A trusted static package is the visual source of truth, but it is not automatically a Pumpkin Page/Theme payload. Tenant creation must not replace it with generic placeholder heroes, shallow summaries, or a silent starter fallback.

## Required Workflow

1. Hash and safety-inventory the source archive. Do not execute uploaded JavaScript.
2. Build a DOM, metadata, route, content, form, interaction, and media relationship inventory.
3. Preserve the original archive separately from the normalized data contract and any runtime fixture.
4. Produce a route parity matrix for every source route, including status, title, H1, metadata, content sections, item/article type, images, forms, links, redirect treatment, and visibility rules.
5. Map item/detail and article structures into supported generic Pumpkin blocks or explicitly supported source-backed HTML. Do not reduce rich detail pages to a hero and CTA.
6. Map media across HTML, CSS, JavaScript text, JSON/data, responsive/lazy attributes, galleries, and dynamic behavior. Deduplicate by content hash only while preserving every source path and alias. Do not flatten filenames or guess URLs.
7. Reimplement required client interactions through reviewed Pumpkin/runtime code. Never copy or execute uploaded JavaScript merely to obtain parity.
8. Generate a Pumpkin-compatible Page/Theme fixture before any live tenant mutation.
9. Prove all-route GET, link, interaction, catalog/detail, blog/article, and form-instance parity at mobile, tablet, and desktop sizes.
10. Require zero broken/pending images, inert controls, unexpected overflow, failed requests, unexpected POST requests, and generic fallback markers.
11. Keep screenshots, browser profiles, fixture output, source packages, binaries, and deployment archives outside the repository.
12. Record owner visual acceptance separately from CMS persistence, deployment, domain cutover, forms, and indexing.

## Party Pros Lessons

- Placeholder compilation can pass schema validation while failing visual fidelity.
- Catalog links are insufficient if item pages lose source-backed specifications, examples, FAQs, planning notes, related items, and supporting media.
- Blog/article and navigation graphs must be compiled as first-class route data, not added after launch.
- Exact metadata, header/footer structure, image relationships, and responsive behavior need explicit comparison.
- Visual repair should remain data-driven and tenant-scoped; it must not silently hard-code another tenant's presentation.
